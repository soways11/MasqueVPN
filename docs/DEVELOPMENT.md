# masquevpn — устройство и разработка

VPN на MASQUE: CONNECT-IP (RFC 9484) поверх HTTP/3/QUIC (`quic-go`).

## Статус

**Этап 1 закрыт (2026-09-17):** настоящие `vpnserver` и `vpnclient` в трёх network
namespace — `ping`, `curl`, UDP и TCP (20 МБ в обе стороны, параллельные загрузки)
проходят через туннель, NAT работает, чёрная дыра MTU закрыта ICMP-обратной
связью. Выход в настоящий интернет проверяется на VPS (в контейнере разработки
UDP наружу закрыт).

- `cmd/vpnserver`, `cmd/vpnclient` — бинарники (сервер — Linux, клиент — Linux
  и Windows), конфигурация в JSON (`deploy/*.example.json`), юниты systemd в
  `deploy/`.
- `cmd/masquevpn-win` — окно клиента для Windows, тот же движок без командной
  строки (см. «Клиенты: Linux и Windows»).
- `internal/clientrun` — запуск клиента целиком: TUN, сессия, маршруты, DNS.
  Общий для консольного клиента и окна, платформенные части — в файлах
  `run_linux.go` / `run_windows.go`.
- `internal/tun` — TUN на Linux (`/dev/net/tun`) и Wintun на Windows, приём
  готового дескриптора (`FromFD` — путь Android `VpnService`).
- `internal/netsetup` — адреса, MTU, маршруты, правила, `ip_forward`, NAT и
  подрезка MSS **через netlink** (rtnetlink + nf_tables) на Linux и через
  IP Helper API на Windows — без внешних `ip`/`nft`/`netsh`.
- `internal/tunnel` — насос клиента и маршрутизатор сервера (адрес → сессия),
  ICMP «слишком большой» пишется обратно в TUN.
- `internal/client` — сборка клиента из конфигурации: транспорт, токен,
  маскировка, ротация, переподключение; платформенно-независим.
- `internal/config` — единый формат конфигурации для всех клиентов.
- `internal/clients` — реестр клиентов: свой ключ у каждого, отзыв, квоты и
  учёт расхода (см. «Клиенты: свой ключ у каждого»).
- `mobile/core` — ядро для Android и iOS: сессия без интерфейса, приём
  готового дескриптора от системы, защита сокета (см. `mobile/README.md`).
- `mobile/android` — приложение на Kotlin: VpnService и один экран.

- `internal/masque` — ядро протокола: Extended CONNECT `connect-ip`, капсулы
  ADDRESS_ASSIGN / ADDRESS_REQUEST / ROUTE_ADVERTISEMENT, IP-пакеты в HTTP Datagrams,
  проверка src/dst по выданным адресам и маршрутам, пул адресов. Поддерживает
  подключаемый `Dialer` (шов для uTLS-транспорта) и `Shaping` (паддинг/джиттер/cover).
- `internal/acme` — сертификат Let's Encrypt автоматически (tls-alpn-01 на
  TCP/443), с продлением без перезапуска и работой на запасном при отказе.
- `internal/site` — встроенный сайт-прикрытие сервера.
- `internal/auth` — аутентификация клиента: токен `ts+nonce+HMAC-SHA256`, окно
  свежести, защита от повтора с ограниченным по памяти кэшем; отказ неотличим
  от обычного 404 (не выдаёт наличие VPN).
- `internal/obfuscation` — политики маскировки трафика для `masque.Shaping`:
  паддинг по «вёдрам», джиттер на мелких пакетах, cover-трафик в простое.
- `internal/fingerprint` — Chrome-подобный профиль транспортных параметров QUIC
  (версия, размер Initial-пакета, окна, keep-alive). См. границу возможного ниже.
- `internal/session` — ротация соединений (make-before-break) против долгоживущих
  сессий; уведомляет о смене адреса.

- `internal/utlsquic` — **транспорт с отпечатком браузера (uTLS)**, опционален,
  собирается тегом `utls`. Внутри — uquic (QUIC с uTLS) плюс свой минимальный HTTP/3.

### Обход DPI: что сделано и граница возможного

Реализовано в рамках MASQUE, без смены транспорта:

0. **Профиль по умолчанию снят с живого Chrome 153** (`chrome-153`, встроен в
   бинарник). Профили из uquic заканчиваются на Chrome 115 образца 2023 года, и
   трёхлетний браузер среди живых — примета сам по себе. Снятый отпечаток несёт
   то, чего в uquic нет вовсе: постквантовый key_share, trust_anchors, новый
   номер ALPS. ECH из записи выбрасывается — см. ниже. Свой отпечаток подставляется файлом (`fingerprint_file`),
   см. «Свежий отпечаток».

1. **Отпечаток QUIC/TLS как у Chrome** — два уровня:
   - `fingerprint` — транспортные параметры через публичный API quic-go (версия,
     размер Initial-пакета, окна, keep-alive). Работает в обычной сборке.
   - `utlsquic` — настоящий ClientHello браузера (сборка `-tags utls`). Измерено
     тестом: расширения Go-клиента `[0 11 65281 23 18 57 5 10 13 16 43 51]` против
     Chrome-профиля `[2570 51 43 0 45 13 10 16 27 17513 57 2570]` — появляются ALPS
     (17513) и compress_certificate (27), исчезают выдающие Go `renegotiation_info`
     (65281), `extended_master_secret` (23), `ec_point_formats` (11). Порядок
     расширений меняется от соединения к соединению, как у настоящего Chrome.
     Значения 2570 по краям — **GREASE**: его во встроенном профиле uquic не было
     вовсе, а «клиент TLS 1.3 без GREASE» не похож ни на один браузер на
     BoringSSL. Добавлен по схеме BoringSSL — в шифронаборы, supported_groups,
     key_share, supported_versions и двумя расширениями по краям.
   - **Серверная сторона**: транспортные параметры по профилю
     (`fingerprint.ServerProfile`), Connection ID длиной 8 байт (умолчание
     quic-go — 4, и эта длина видна в каждом пакете клиента), ответ stateless
     reset на незнакомый Connection ID и Version Negotiation на незнакомую
     версию — как у настоящего развёртывания.
2. **Аутентификация + защита от активного зондирования** (`auth` + `Authorize`/`Fallback`).
3. **Паддинг, джиттер, cover-трафик** (`obfuscation` + `masque.Shaping`).
   Интервалы cover и период keep-alive — **случайные** (пуассоновский поток):
   постоянный период сам по себе метроном, то есть признак туннеля. Измерено:
   коэффициент вариации интервалов ≈ 1.0 против 0 у константы.
   Профили `CloudGamingUpstream/Downstream` асимметричны — вверх мелкие пакеты
   (ввод игрока), вниз крупные (видеокадр), как у облачного гейминга.
4. **Ротация соединений** (`session`) — со случайным разбросом срока
   (`rotation.jitter`, по умолчанию ±25%): ровная периодичность рукопожатий
   видна наблюдателю в открытую и была бы тем же метрономом.
5. **Маскировка семантики протокола** — сессия предъявляется как **WebTransport**
   (`:protocol = webtransport` + SETTINGS `0x2b603742`/`0xc671706a`). Это убирает
   главную улику: датаграммы на HTTP/3 перестают быть аномалией, потому что
   WebTransport-приложения (облачный гейминг, live-видео) их и используют.
   Внутри — те же капсулы CONNECT-IP, ядро не меняется.
6. **Фоновые DNS-запросы мимо туннеля** (`internal/dnscover`). Когда весь
   трафик уходит в туннель, вместе с ним уезжает и DNS: снаружи получается
   машина, которая часами льёт объём на один адрес и почти не спрашивает
   имён. Признак дешёвый — виден на одних потоках, без разбора содержимого,
   и от качества отпечатка не зависит. Клиент шлёт настоящие запросы к тому
   резолверу, которым система пользовалась до подключения, помеченным
   сокетом (мимо туннеля): A и AAAA одной группой из одного сокета, иногда
   HTTPS RR, интервалы пуассоновские. Имена — только из списка (по
   умолчанию два десятка обычных адресов плюс домен своего же сервера:
   обычный клиент резолвит имя, к которому подключается). Настоящий DNS
   пользователя по-прежнему целиком внутри туннеля, наружу не выносится
   ничего; случайные поддомены не используются — это был бы признак
   DNS-туннеля. Включено по умолчанию при полном туннеле, выключается
   `"dns_cover": {"disabled": true}`.
7. **Прикрытие потоками** (`masque.CoverBrowsing`) — клиент фоном делает обычные
   HTTP/3 GET-запросы к сайту-прикрытию по тому же соединению. Лечит
   «ровно один поток живёт часами» и перекос «весь объём датаграммами».

Порт сервера — любой (задаётся в адресе), жёсткой привязки к UDP/443 нет.

8. **Развязка «пакет ↔ датаграмма»** (`masque.Packing`, кадры в датаграмме).
   Раньше один IP-пакет всегда ехал в одной датаграмме: паддинг ломал
   размеры, но не количество и не ритм, и всплеск из десяти пакетов внутри
   был снаружи всплеском ровно из десяти датаграмм. Теперь между TUN и
   проводом стоит упаковщик:
   - несколько мелких пакетов складываются в одну датаграмму (окно
     агрегации по умолчанию 300 мкс — залп TCP-подтверждений уезжает одной
     датаграммой: измерено, 50 пакетов → 1 датаграмма);
   - крупный пакет режется на куски и собирается на приёме (устойчиво к
     переупорядочиванию и повторам, с потолком и таймаутом);
   - при заданном профиле (`packing.pace`) датаграммы уходят по расписанию,
     а не по мере поступления пакетов, и в простое тоже. Измерено: 4 пакета
     внутри за секунду → 97 датаграмм одинакового размера снаружи.
   Формат согласуется капсулой: со старой версией на том конце обмен идёт
   по-прежнему. Расписание под нагрузкой уступает пропускной способности —
   иначе скачивание упёрлось бы в темп профиля.
9. **Отпечаток серверной стороны** (`fingerprint.ServerProfile`). Клиент
   выглядел как Chrome, а сервер отвечал умолчаниями quic-go — вторая
   половина рукопожатия сводила на нет работу над первой. Теперь
   транспортные параметры сервера задаются профилем (время простоя, окна,
   лимиты потоков, размер пакета, stateless reset). Профиль можно снять с
   живого сервера утилитой `fpserver` и подставить файлом.
10. **Остаточные признаки**: cover-трафик идёт и под нагрузкой (иначе его
    появление само размечает границы активности), TLS-сессия возобновляется
    по билету при ротации и переподключении (полное рукопожатие каждый раз —
    аномалия), на сессию есть потолок полосы, поток неизвестных капсул
    ограничен.

### Корректность работы с трафиком

- **Сообщения об MTU.** Пакет, не помещающийся в датаграмму, больше не исчезает
  молча: `WritePacket` возвращает `*PacketTooLargeError` с готовым ICMP
  (`Fragmentation Needed` для IPv4, `Packet Too Big` для IPv6), который слой TUN
  записывает обратно в интерфейс. Без этого получалась «чёрная дыра MTU»: мелкие
  пакеты проходят, крупные пропадают, TCP-соединение устанавливается и виснет.
  `Conn.MaxPacketSize()` отдаёт выясненный предел.
- **Двойной стек.** `ServerConfig.Pools` — по пулу на семейство адресов, клиент
  получает адрес из каждого. С единственным пулом работал бы только IPv4 или
  только IPv6, и половина трафика шла бы мимо туннеля.
- **IPv6 на сервере.** По умолчанию адреса из `pool6` маскарадятся так же,
  как IPv4 (NAT66). Если хостер выдал маршрутизируемый префикс — включите
  `"nat": {"no_ipv6": true}` и раздавайте адреса из него: NAT66 ломает
  сквозную адресацию без пользы. Если `pool6` задан, а маршрута IPv6 наружу
  у сервера нет, сервер предупреждает: клиент предпочтёт IPv6 и уйдёт в
  чёрную дыру.
- **Часы.** Токен привязан ко времени (±30 с). Если часы клиента разъехались,
  сервер отвечает ему ровно как постороннему — 404. Клиент сверяет свои часы
  с заголовком `Date` из ответа и пишет об этом прямо, иначе такую поломку
  ищут часами. На сервере нужен NTP.
- **Изоляция клиентов.** Сервер не пропускает пакеты на туннельные адреса других
  клиентов: маршруты по умолчанию — весь интернет, а он включает и туннельную
  сеть. Снимается через `AllowClientToClient`.
- **Сохранение адреса при ротации.** `session.Config.KeepAddress` — после ротации
  клиент забирает прежний адрес обратно через ADDRESS_REQUEST, иначе каждая
  ротация рвала бы все соединения внутри туннеля.
- **Прикрытие потоками в uTLS-пути.** Фоновые GET-запросы теперь работают в обоих
  транспортах, а не только в quic-go.

### Лимиты ресурсов и корректность протокола

- `masque.Limits` — потолок одновременных сессий всего и с одного адреса,
  закрытие по простою, потолок капсул ADDRESS_REQUEST на сессию. Отказ по лимиту
  не расходует адрес из пула.
- `auth.Options.MaxReplayEntries` — потолок кэша защиты от повтора.
- **IPv6 extension-заголовки** обходятся при разборе пакета. Раньше в поле
  протокола попадал тип первого extension-заголовка, и маршрут с указанным
  `IPProtocol` отбрасывал легитимные пакеты (например, фрагментированные).
- **ADDRESS_REQUEST с конкретным адресом** учитывается: если адрес свободен,
  сервер выдаёт именно его и возвращает прежний в пул.
- **Адрес закреплён за клиентом, а не за сессией.** В токене едет псевдоним
  установки (`client_id`, 8 байт, подписан тем же HMAC), и сервер держит за ним
  аренду адресов (`limits.address_lease_ttl`, по умолчанию 2 минуты). Поэтому
  при ротации новая сессия открывается сразу со своим адресом, а после обрыва
  или смены сети клиент получает прежний — соединения внутри туннеля не рвутся.
  Без этого передача вставала на каждой ротации: клиент слал пакеты со старым
  адресом, а сервер отбрасывал их как чужие. `client_id` не секрет; если его не
  задать, он случайный на время работы процесса (тогда адрес не переживает
  перезапуск клиента).

## Запуск

Разворачивание на VPS одной командой — `deploy/vps/` (`install.sh`, `diag.sh`,
`uninstall.sh`, README рядом). Поддерживаются оба случая: свободный TCP/443 с
ACME и занятый TCP/443, когда masquevpn встаёт на UDP/443 рядом с чужим nginx
(см. «Сайт-прикрытие»).

```sh
go build -o vpnserver ./cmd/vpnserver
go build -tags utls -o vpnclient ./cmd/vpnclient   # клиент с отпечатком браузера

./vpnserver genkey > /etc/masquevpn/auth.key           # общий ключ клиентов
./vpnserver clients add -name "Ноутбук"              # или ключ на каждого
./vpnserver -config /etc/masquevpn/server.json         # см. deploy/server.example.json
./vpnclient -config /etc/masquevpn/client.json         # см. deploy/client.example.json
./vpnclient -config client.json -check             # только проверить конфигурацию
```

Оба бинарника требуют root (TUN, маршруты, nf_tables, `SO_MARK`). Внешние
утилиты не нужны. SNI — домен из `server` (или `server_name`), в открытом виде;
ECH не используется.

**Сервер:** TUN с адресом шлюза (первый адрес пула), `ip_forward`, таблица
nf_tables `inet masquevpn` (masquerade + подрезка MSS), маршрутизатор «адрес →
сессия». Обычный запрос (GET и прочие) получает сайт-прикрытие; CONNECT, не
прошедший проверку, — ответ обычного сервера (405/501/404), а не страницу
сайта. При остановке таблица NAT удаляется.

**Клиент, полный туннель** (как wg-quick): сокет QUIC помечается `SO_MARK`,
правило `not fwmark → таблица 7443 (default dev masquevpn0)` и правило
`lookup main suppress_prefixlength 0`. Петли нет, локальная сеть остаётся
доступной, смена сети/шлюза ничего не ломает. IPv6 заворачивается в туннель
всегда — даже если сервер его не выдал: тогда он упирается в интерфейс без
адреса, а не утекает мимо. Имя сервера разрешается мимо туннеля (помеченным
сокетом) — иначе переподключение было бы невозможно.

**Обрыв и ротация:** клиент переподключается сам (пауза 0,5 → 30 с), просит
прежний адрес (ADDRESS_REQUEST) и сообщает смену адреса интерфейсу, только
если вернуть его не удалось. Во время ротации с `keep_address` пакеты со
старым адресом уходят через старое соединение — паузы в трафике нет.

**DNS:** `dns` в конфигурации клиента временно подменяет `/etc/resolv.conf`
(оригинал переименовывается и возвращается при выходе, в том числе после
аварийного завершения — при следующем запуске). Параллельно работает
прикрытие `dns_cover` (см. выше): адреса резолверов для него берутся из
исходного `resolv.conf` ДО подмены, а заглушка systemd-resolved (127.0.0.53)
заменяется вышестоящими адресами из `/run/systemd/resolve/resolv.conf` —
запрос к заглушке ушёл бы внутрь туннеля и снаружи не появился бы.

## Профили: несколько доступов в одном клиенте

```sh
vpnclient -profile-add "masquevpn://…"            # из ссылки, имя берётся из неё
vpnclient -profile-add work.json              # из файла, имя — из имени файла
vpnclient -profiles-list                      # что есть и что выбрано
vpnclient -profile-use работа                 # переключиться
vpnclient -profile-remove работа
```

Профили лежат в `profiles.json` рядом с программой (права 0600, внутри
ключи). Рядом, а не в профиле пользователя: клиент работает от
администратора, и файл в его AppData невидим для того, кто запустил
программу двойным щелчком; и рядом, а не в ProgramData, — чтобы папку можно
было перенести на флешке вместе со всеми доступами.

Импорт **не переключает** выбранный профиль: туннель может быть поднят, и
переключение окажется неожиданностью. Клиент об этом говорит и подсказывает
команду. Повторный импорт того же имени заменяет конфигурацию — человек,
которому перевыдали доступ, чинит его, а не заводит «домашний (2)».

Явный `-config` главнее профилей: у тех, у кого рядом лежит `client.json`,
от появления профилей ничего не меняется. При работе по профилю его имя
пишется в журнал — «подключён» без уточнения, куда именно, это половина
ответа.

## Клиенты: Linux и Windows

Движок подключения один на обе системы — `internal/clientrun`. Различается
только платформенный слой: как открывается TUN и как правится сеть.

|  | Linux | Windows |
|---|---|---|
| TUN | `/dev/net/tun` | Wintun (`wintun.dll` рядом с программой) |
| настройка сети | netlink (rtnetlink) | IP Helper API (`iphlpapi.dll`) |
| трафик туннеля мимо туннеля | `SO_MARK` + правило `not fwmark` | маршрут-исключение /32 к серверу через прежний шлюз |
| полный туннель | таблица 7443, `default dev masquevpn0` | половинки `0.0.0.0/1` и `128.0.0.0/1` |
| DNS | подмена `/etc/resolv.conf` | `SetInterfaceDnsSettings` + сброс кэша |
| права | root | администратор (UAC) |

Внешних утилит не вызывает ни та, ни другая сборка: ни `ip`, ни `netsh`.

```sh
# Linux
go build -tags utls -o vpnclient ./cmd/vpnclient
sudo ./vpnclient -config client.json

# Windows (кросс-сборка с Linux)
GOOS=windows GOARCH=amd64 go build -tags utls -o masquevpn-cli.exe ./cmd/vpnclient
GOOS=windows GOARCH=amd64 go build -tags utls -ldflags "-H=windowsgui" \
    -o masquevpn.exe ./cmd/masquevpn-win
```

Рядом с `.exe` должна лежать **wintun.dll** (файл берётся с wintun.net,
каталог `bin/amd64`): в ней же приезжает и сам подписанный драйвер, он
ставится при создании адаптера. Драйвер от авторов WireGuard; TAP-драйвер
OpenVPN не взят сознательно — он работает на канальном уровне, пришлось бы
самим отвечать на ARP и снимать заголовки Ethernet ради того же результата.

**Окно (`cmd/masquevpn-win`)** — то же самое, но без командной строки: состояние,
кнопка, путь к конфигурации и журнал. Написано прямо на Win32 (`user32`,
`gdi32`), без фреймворка интерфейса: любой из них — внешняя зависимость, а
проект собирается без доступа к сети. Прав администратора окно не просит у
пользователя словами — если их нет, оно перезапускает себя через UAC
(`ShellExecute "runas"`). О том, что туннель поднялся, окно узнаёт не из
текста журнала, а вызовом `clientrun.Hooks.Up` — движок сообщает о себе сам.

**Экраны и размер окна** (Windows и Linux — раскладка общая, `internal/gui`).
Экранов четыре: подключение, настройки, добавление сервера и журнал. Журнал —
отдельный экран со стрелкой «назад», кнопкой «Копировать» и прокруткой
колесом; строки переносятся по измеренной ширине шрифта (`gui.LogChars`),
новые записи не сдвигают то, что человек читает в середине. Высота окна одна
на все экраны (`gui.DefaultWinH`, 640 точек) и сама не меняется — ни от
экрана, ни от числа профилей: раньше окно прыгало при каждом переходе. Меняет
её только человек, потянув нижний край (от `MinWinH` до `MaxWinH`; ширина
неизменна), и выбранная высота запоминается в `window.json` рядом с
профилями. Профили на главном экране — сколько влезло, остальные строкой
«ещё N — в настройках». Переключателя «Весь трафик через VPN» в окнах нет:
выключенный, он без списка сетей (а его в окне не задать) давал профиль,
который не подключался; такие профили при загрузке возвращаются в полный
туннель. Раздельный туннель остался — полем `routes` в файле профилей.

**Самопроверка платформенного слоя Windows** (без сервера и без сети):

```
masquevpn-cli.exe -selftest            # адаптер, адрес, MTU, маршрут, DNS
masquevpn-cli.exe -selftest-full -selftest-seconds 20   # ещё и полный туннель
```

Она создаёт адаптер, назначает адрес и MTU, добавляет маршрут, проверяет
`GetBestRoute2`, ставит и возвращает DNS, при `-selftest-full` поднимает и
снимает полный туннель — и всё за собой убирает.

Проверено на живой Windows 11 (26200): Wintun 0.14, адрес и MTU прочитаны
обратно, маршрут подтверждён, DNS назначен и возвращён; при полном туннеле
система отправляет 8.8.8.8 в адаптер (половинки перебили маршрут по
умолчанию), а адрес сервера — мимо него (исключение /32 работает); после
выхода таблица маршрутов побайтно исходная и интернет на месте.

**IPv6 заворачивается на самом деле** — это стоило проверить отдельно.
Половинки `::/1` и `8000::/1` кладутся на адаптер, у которого адреса IPv6 нет
вовсе, и из документации не следует, что Windows такой маршрут вообще примет,
не говоря уже о предпочтении его маршруту провайдера. Если бы не приняла,
получился бы худший исход: IPv4 в туннеле, IPv6 в открытую, а пользователь
видит «подключено». Измерено на машине с живым IPv6: до туннеля путь к
`2606:4700:4700::1111` шёл через физический интерфейс, после — через адаптер.
Самопроверка сравнивает именно «до» и «после»: спрашивать только после
бессмысленно, потому что маршрут к этому моменту наш в любом случае — и на
машине без IPv6 проверка отрапортовала бы успех, ничего не проверив.

Структуры IP Helper API описаны вручную, поэтому их размеры закреплены
тестами (`netsetup_windows_test.go`): расхождение в выравнивании даёт не
ошибку компиляции, а порчу памяти в чужом коде.

### Аварийное отключение (kill switch, Windows)

```jsonc
"kill_switch": false     // по умолчанию ВКЛЮЧЕНО при full_tunnel
```

```jsonc
"kill_switch_allow": ["203.0.113.7", "198.51.100.0/24"]
```

Пока kill switch включён, наружу выпускаются только туннель, петля, локальная
сеть, **адрес сервера** и то, что перечислено в `kill_switch_allow`. Сервер и
резолверы прикрытия DNS добавляются автоматически — второе важно: запросы
прикрытия обязаны идти к резолверу провайдера мимо туннеля, иначе они не
прикрытие, и без этого они упирались бы в собственную блокировку. Список нужен
для стороннего, о чём знает только пользователь: другой прокси-клиент,
рабочий VPN, устройство в чужой подсети. Без него такие соединения рвутся
молча, и причину ищут снаружи.

При штатном отключении клиент снимает маршруты сам. Но если он падает — краш,
снятие задачи, выключение по питанию, — адаптер Wintun исчезает вместе с
маршрутами, и система молча возвращается к обычному шлюзу: отказ туннеля
ОТКРЫВАЕТ трафик. Kill switch закрывает эту дыру через Windows Filtering
Platform: пока он включён, наружу выпускаются только адрес сервера, локальная
сеть и петля, а всё прочее исходящее блокируется в ядре, мимо маршрутизации.

**Блокировка живёт ровно столько, сколько жив процесс клиента.** Подслой и
фильтры создаются в динамической сессии WFP, и Windows снимает их сама, как
только закрывается дескриптор движка — в том числе если процесс умер, не
закрыв его. Запереть машину без сети невозможно.

Плата названа прямо: при падении клиента трафик **открывается** (fail-open), а
не остаётся закрытым. Это размен «пользователь на минуту без VPN» против
«пользователь без интернета до переустановки системы» — и он выбран
сознательно, после того как первая версия с персистентными фильтрами заперла
живую машину. Режим «пережить крах процесса» возможен, но только отдельным
явным флагом, и его пока нет.

**Что остаётся после смерти клиента и кто это убирает.** Блокировка WFP
умирает вместе с процессом. А правило разрешения имён (реестр) и
маршрут-исключение к серверу — нет: их снимает сам клиент при выходе, а
снятой задаче выходить нечем. Молча оставленное правило уводит весь системный
DNS на резолвер за туннелем, которого больше нет; снаружи это выглядит как
«интернет работает, а часть соединений не устанавливается».

Поэтому клиент, подняв полный туннель, запускает **сторожа** — отдельный
отсоединённый процесс, который ждёт его завершения и прибирается. При штатном
выходе клиент убирает сам и гасит сторожа. Если снять обе задачи разом,
уберёт следующий запуск клиента или команда:

```
vpnclient -cleanup          # прежнее имя: -killswitch-off
```

Она снимает блокировку, правило имён и маршруты, работает без конфигурации и
без поднятого туннеля и безвредна, когда снимать нечего. Клиент вызывает её и
сам при каждом запуске. Внутри важен порядок: сначала удаляются фильтры, потом
подслой. Наоборот нельзя — Windows не удаляет подслой, пока в нём есть
фильтры (`FWP_E_IN_USE`), и именно на этом первая версия молча «снимала»
блокировку, которой не снимала. Клиент вызывает этот выход и сам при каждом
запуске.

Проверено на живой машине против боевого сервера. Разницу видно только на
соединении, привязанном к физическому адаптеру (`curl --interface <адрес
Wi-Fi>`) — так ходят WebRTC и часть служб, и таблица маршрутов их не
останавливает:

| проверка | без kill switch | с kill switch |
|---|---|---|
| обычный трафик | адрес сервера | адрес сервера |
| соединение, привязанное к Wi-Fi | **домашний адрес — утечка** | блок |
| DNS | — | резолвер за туннелем |
| сервер остановлен, клиент жив | — | трафика нет, утечки нет |
| перезапуск сервера | — | клиент переподключился сквозь блок |
| снятие задачи клиента | — | сеть вернулась сама |

Конструкция закреплена тестом `TestKillSwitchConstruction`: он читает исходник
и следит, чтобы не вернулись персистентные фильтры, динамическая сессия и
порядок снятия. Обычным тестом это не поймать — нужен настоящий WFP, — а цена
ошибки здесь выше обычной.

### MTU

В датаграмму помещается меньше, чем в обычный пакет: заголовки QUIC, AEAD-тег,
кадр DATAGRAM, Quarter Stream ID и Context ID. Реальные потолки IP-пакета
(измерены сквозным тестом):

| путь | потолок |
|---|---|
| клиент → сервер, quic-go (пакет 1350) | 1304 |
| клиент → сервер, uTLS (после PMTUD) | 1322–1372 |
| сервер → клиент, quic-go (пакет 1350) | 1304 |

Отсюда MTU TUN по умолчанию — **1280** (минимум IPv6).

**Цена фрагментации:** пакет в 9 КБ — это восемь датаграмм, и потеря любой
убивает весь пакет (датаграммы QUIC не переотправляются). На канале с
потерями большой MTU теперь вредит сильнее, чем раньше: поднимать его стоит
там, где потерь мало.

**С кадрами (по умолчанию) потолок перестал быть жёстким:** пакет крупнее
датаграммы режется на куски, и MTU 1500 работает, не требуя ICMP вовсе —
проверено сквозным тестом (ядро клиента не узнаёт никакого уменьшенного
MTU). ICMP-обратная связь осталась для случая, когда на том конце старая
версия без кадров: там MTU 1500 работает за счёт ICMP, а без него
(mutation-проверка) TCP виснет до таймаута.

Найдено и обойдено по пути (подробности — в комментариях к коду):

- **quic-go v0.59**: после первого ACK оценка «сколько влезает в датаграмму»
  подменяется сырым размером пакета — датаграммы в полосе ~40 байт под
  потолком принимались и молча терялись. Поправка в `masque/stream.go`,
  PMTUD у quic-go выключен.
- **uquic v0.0.6** вообще не сверяет датаграмму с размером пакета. Потолок
  считает наш HTTP/3 по трассировке соединения (`utlsquic/mtu.go`), включая
  рост через PMTUD. Стартовый пакет uquic — 1252 байта, в датаграмму влезает
  ~1220 < 1280, поэтому клиент после подключения до 5 с ждёт первых проб
  PMTUD (`Conn.WarmUp`; на практике ~0,1 с).
- «Ведро» паддинга крупнее пути превращало проходимые пакеты в ICMP; теперь
  паддинг урезается под потолок.
- Джиттер был блокирующим сном в насосе: скачивание упиралось в ~30 Мбит/с.
  Теперь задержанные пакеты уходят через отдельную очередь (порядок
  сохраняется) — 190–300 Мбит/с на стенде, как и без маскировки.

**Известное ограничение:** quic-go держит на поток HTTP/3 лишь 32
непрочитанные датаграммы. Датаграммы выбираются отдельной горутиной
(`Conn.recvLoop`), но залп длиннее 32 при медленном планировании может
частично теряться — для TCP это обычная потеря. Полное решение — собственный
разбор датаграмм на уровне QUIC-соединения (`http3.Server.ConnContext`).

### Запасные UDP-порты

Провайдеры режут UDP по номеру порта, не глядя в содержимое (25.09: UDP/443
у домашнего подключения не проходил вовсе, 4443 — проходил). Браузер от
такой блокировки откатывается на TCP, нам некуда: транспорт — только QUIC.
Ответ в рамках MASQUE — другой UDP-порт.

**Сервер** слушает основной порт из `listen` и запасные из `alt_ports` —
один HTTP/3-сервер, по слушателю на порт; все сокеты открываются до запуска,
занятый запасной порт — ошибка старта, а не тихо пропавший порт:

```jsonc
"listen":    ":443",
"alt_ports": [8443, 2053, 2083, 2087, 2096]   // стандартный набор — config.DefaultPorts
```

`vpnserver ports -config … [-set 8443,2053|default]` показывает и меняет их
разбором JSON (порядок полей сохраняется, результат проверяется до записи,
прежний файл — копией). TCP-слушатель и `Alt-Svc` от запасных портов не
зависят.

**Клиент** получает порты прямо в адресе: `"server": "vpn.example.com:8443,2053,2083"`.
Не отдельным полем сознательно: адрес — единственное, что форма «добавить
сервер» показывает и правит во всех трёх клиентах, и отдельное поле терялось
бы при вставке ссылки и правке профиля. `clients add` дописывает порты из
конфигурации сервера сам (порт из `-server` — первым; `-single-port` — без
них, для клиентов до 0.4.0, которые такой адрес не разбирают).

Дозвон (`client.Dialer.Dial`) начинает с порта, ответившего в прошлый раз,
и идёт по кругу. На следующий порт переходит, только когда этот **молчит**:
таймаут рукопожатия QUIC (5 с тишины; на все порты, кроме последнего, ещё
и предел 8 с), ICMP «порт недоступен» или отказ локального файрвола
(EPERM/EACCES при отправке). Ответ сервера — 404, чужой сертификат, неверный
ключ — возвращается сразу: другой порт его не исправит. Ни один не ответил —
`client.PortsError`: «порты 8443, 2053 не отвечают: закрыты по пути или
сервер выключен» (помещается в окно — две строки по 50 знаков). Срок первого
подключения (`ConnectTimeout`) и переподключения растёт с числом портов.

Проверено сквозным тестом (`test/e2e/ports_test.go`): UDP/443 молча
отбрасывается на входе сервера — клиент за ~5 с уходит на 8443 и туннель
работает (оба стека QUIC); закрыты оба — понятная ошибка; порт закрыт
файрволом самого клиента — тоже переход.

### Обычный HTTPS по TCP

Сервер слушает не только UDP/443 (HTTP/3), но и TCP/443, отдавая там тот же
сайт-прикрытие и заголовок `Alt-Svc: h3=":443"`. Без этого получался домен, у
которого HTTP/3 есть, а обычного HTTPS нет, — аномалия, видимая одним `curl`;
вдобавок браузеру неоткуда узнать про HTTP/3, потому что Alt-Svc приходит
именно по TCP. Выключается `"tcp": {"disabled": true}`, отдельный адрес —
`"tcp": {"listen": ":8443"}`.

### Клиенты: свой ключ у каждого, отзыв и квоты

Простой режим — один общий ключ (`auth_key`) на всех. Он работает, но из него
следуют три вещи сразу: получивший ключ неотличим от законного владельца;
отозвать доступ одному нельзя — только сменить ключ и разослать новый всем
остальным; и посчитать, кто сколько израсходовал, не на чем.

Реестр клиентов это закрывает:

```jsonc
"clients_file": "/etc/masquevpn/clients.json"   // вместо auth_key
```

Вместе с `auth_key` не работает и отвергается конфигурацией: общий ключ рядом
с личными — чёрный ход, по которому отозванный заходит как ни в чём не бывало.

```sh
vpnserver clients add -name "Ноутбук" -quota 200GB -max-sessions 4
vpnserver clients list
vpnserver clients show    -id 1a2b3c4d5e6f7a8b
vpnserver clients disable -id 1a2b3c4d5e6f7a8b     # приостановить
vpnserver clients enable  -id 1a2b3c4d5e6f7a8b     # вернуть
vpnserver clients remove  -id 1a2b3c4d5e6f7a8b     # удалить
```

```sh
vpnserver clients add -name "Ноутбук" -out /root/laptop.json
```

С `-out` в терминал не выходит **ни ключ, ни ссылка**: ссылка несёт тот же
ключ, и печатать её рядом со словами «ключ не показан» было бы обманом.
Рядом с конфигурацией ложится `laptop.link` — та же выдача одной строкой:

```
masquevpn://eyJhdXRoX2tleSI6...#Ноутбук
```

Строку можно переслать и вставить в клиент на компьютере или телефоне (см.
«Профили»), из неё же делается QR-код. Без `-out` и конфигурация, и ссылка
печатаются, но клиент предупреждает, что они осели в истории терминала.

**Выдаётся минимум полей** — `server`, `auth_key`, `client_id`. Остальное
клиент подставляет сам: полный туннель, IPv6, транспорт с отпечатком
браузера, метка WebTransport, резолвер, ротация, прикрытие DNS и потоками,
аварийное отключение. Лишние строки в конфигурации не бесплатны: человек
перестаёт замечать те, которые стоит менять.

### Резервная копия реестра

```sh
vpnserver clients backup                     # рядом с реестром, с датой в имени
vpnserver clients backup -out /root/keys.json
vpnserver clients restore -from /root/keys.json
```

В реестре лежат ключи всех клиентов, и восстановить их неоткуда: они
генерируются при выдаче и больше нигде не хранятся. Потеря файла отключает
всех разом, причём самый вероятный способ его потерять — не отказ диска, а
человек: переустановка, `rm` не в том каталоге, переезд на другой сервер.

В копию входит и файл учёта расхода: порознь они расходятся, и клиент,
исчерпавший месячную квоту, получил бы её обратно. Копия — обычный JSON с
правами 0600: её можно открыть и посмотреть, что внутри.

Восстановление сначала откладывает текущие файлы рядом
(`.before-restore`) — восстановление «не из той» копии само по себе потеря
доступа. Копия без клиентов, чужой JSON и испорченный реестр отвергаются с
объяснением, а не перезаписывают реестр молча.

**Как это работает.** Псевдоним клиента (8 байт) и раньше ездил в токене
подписанным — за ним закреплялась аренда адреса. Теперь у него вторая роль:
по нему сервер находит, КАКИМ ключом проверять подпись. Псевдоним не секрет,
секрет — ключ. Неизвестный псевдоним получает ключ-пустышку, и HMAC считается
всё равно: иначе по времени ответа перебиралось бы, какие клиенты существуют.

**Отзыв доходит до уже подключённых.** Токен проверяется один раз, при
открытии сессии, поэтому одного удаления записи мало: сессия жила бы дальше, а
переподключения может не случиться неделями. Сервер перечитывает реестр
(`clients_reload`, по умолчанию 10 с) и закрывает живые сессии тех, кто
потерял доступ, возвращая их адреса в пул. Ошибка чтения реестра никого не
отключает: битый или временно недоступный файл — куда чаще опечатка, чем
намерение закрыть доступ всем сразу.

**Квоты и полоса — на клиента, а не на сессию.** Иначе и то и другое обходится
открытием второй сессии. `quota` + `period` (`month`, `day`) ограничивают
объём, `max_bytes_per_second` — полосу, `max_sessions` — число одновременных
сессий. Исчерпанная квота не пускает в новую сессию и закрывает текущие:
сессию, открытую до исчерпания, иначе ничто бы не остановило. Расход считается
по таймеру (не на каждом пакете) и сохраняется в `<clients_file>.usage` —
без сохранения квота обнулялась бы перезапуском.

**Цена, о которой стоит сказать прямо.** Реестр делает трафик
**атрибутируемым**: с общим ключом сервер не знал, чей поток обслуживает,
теперь знает. Для своего сервера на несколько человек это выигрыш в
управляемости; при раздаче широкому кругу — свойство, о котором надо
предупреждать.

### Сертификат: автоматический (ACME)

```jsonc
"acme": {
  "domains": ["vpn.example.com"],
  "email":   "admin@example.com",      // туда придёт письмо об истечении
  "cache_dir": "/var/lib/masquevpn/acme"   // ключ аккаунта и сертификаты
}
```

Сервер сам получает сертификат Let's Encrypt и сам его продлевает — без
перезапуска и без внешнего certbot. Проверка идёт по **tls-alpn-01** на том же
TCP/443, где стоит сайт-прикрытие: отдельный HTTP-порт и доступ к DNS-зоне не
нужны, поэтому `tcp` должен быть включён и слушать 443 (конфигурация это
проверяет).

`cert_file`/`key_file` при включённом ACME не обязательны, но если заданы —
работают запасными: пока сертификат не получен или удостоверяющий центр
недоступен, сервер отвечает ими, а не падает. Выдача вынесена из рукопожатия:
клиент не ждёт ACME дольше пяти секунд, попытка доводится в фоне, и чаще чем
раз в десять минут сервер за сертификатом не ходит — у Let's Encrypt лимиты на
заказы. Для обкатки удобен `"directory_url"` на staging: лимиты мягче, но
сертификат не доверенный.

Каталог `cache_dir` надо сохранять между перезапусками: в нём ключ аккаунта и
сами сертификаты, иначе каждый запуск — новый заказ.

### Сайт-прикрытие

Пробер, постучавшись в домен, должен видеть работающий сайт. Варианты, в
порядке убывания силы:

```jsonc
"fallback_proxy": "http://127.0.0.1:8080",  // реверс-прокси на живой backend
"fallback_dir":   "/var/www/html",          // статика из каталога
"fallback_site": {                          // встроенный сайт (по умолчанию)
  "contact":     "hello@example.com"          // title, description — по желанию
}
```

Если не задано ничего, поднимается встроенный сайт: связанные страницы,
ассеты с версией в имени и вечным кэшем, ETag/304, gzip, свои 404 и 405,
`robots.txt`, `sitemap.xml`, favicon и живой фид статуса в JSON.

**Чем сайт одной установки отличается от другой.** Код публичный, поэтому
одинаковый у всех текст находился бы одним поисковым запросом, а
выведенный из домена — вычислялся бы по домену и сверялся побайтно. Отсюда
правило: из домена берётся только название (`vpn.quiet-river.io` → Quiet
River), как у любого настоящего сайта, а всё остальное — из секретного
случайного seed'а установки:

- легенда сервиса (сейчас шесть: доставка сообщений, сбор метрик, кэш
  сборок, ресайз картинок, вебхуки, синхронизация) — описание, блоки на
  главной, разделы документации, компоненты на странице статуса;
- пути документации (`/docs`, `/documentation`, `/guide`, `/developers`) и
  фида статуса (`/api/status.json`, `/api/v1/status`, `/status.json`,
  `/api/health`), подписи в меню;
- акцент, шрифт, скругления, ширина, размер заголовка, а с ними — имена
  ассетов.

Seed лежит в `/var/lib/masquevpn/site-seed` (0600) и создаётся сервером при
первом запуске — конфигурацию для этого править не нужно. Задать вручную:
`"seed"` (строка от 16 символов) или `"seed_file"` в `fallback_site`.
Пропажа файла ничего не ломает, но сайт станет другим — как после смены
дизайна; при переезде на новый VPS его стоит перенести вместе с реестром.
Название «Nimbus Lab» и описание, которые установщик вписывал до
28.09.2026, сервер считает незаданными, а install.sh убирает их из
конфигурации.

Разметка всё равно общая, так что тот, кто ищет именно masquevpn, сайт
узнает. Против этого — только `fallback_proxy` на настоящий backend.
Отключается `"fallback_site": {"disabled": true}` — тогда посторонний видит
404, и сервер предупреждает об этом в журнале.

Ответ на CONNECT сайту не отдаётся ни в одном из вариантов: обычный сервер
документ на этот метод не возвращает, и 200 со страницей был бы признаком в
один запрос. Чужой маршрут и непрошедшая проверка токена отвечают одинаково,
байт в байт, — по ответу нельзя узнать, есть ли у домена туннельный путь.

### Профиль сервера и его снятие

```sh
go build -o fpserver ./cmd/fpserver
./fpserver -probe cloudflare-quic.com:443              # посмотреть чужие параметры
./fpserver -probe cloudflare-quic.com:443 -out srv.json # снять профиль
# в конфигурации сервера: "server_profile_file": "srv.json"
```

**По умолчанию — `cloudflare`:** профиль, снятый с живого `www.cloudflare.com`
и встроенный в бинарник (`internal/fingerprint/profiles/`). Файл нужен только
чтобы подставить свой. `"server_profile": "cdn"` возвращает прежнюю эвристику
(выдуманные числа порядков величин), `"stock"` — умолчания quic-go, по которым
сервер узнаётся сразу.

**Снятый профиль неполон по устройству, и это учтено при загрузке.** Часть
того, чем отличается сервер, транспортными параметрами не объявляется, а
значит и снятию не поддаётся:

- *размер пакета* — в файле его нет, и ноль означал бы умолчание quic-go
  (1280 вместо 1350), то есть потолок датаграммы ниже примерно на 70 байт;
- *длина Connection ID* — ноль вернул бы 4 байта quic-go, ровно тот признак,
  по которому сервер на quic-go отличается от живого CDN одним пакетом;
- *датаграммы* — их не объявляет ни Cloudflare, ни Google, так что из снятого
  профиля они прийти не могут в принципе, а без них нет CONNECT-IP.

Первые два дозаполняются при чтении файла, датаграммы включаются всегда.

**Окна: объявляем снятое, расти даём больше.** В параметрах видно только
НАЧАЛЬНОЕ окно; потолок его роста наружу не виден, потому что проявляется
лишь в зашифрованных MAX_DATA. Занижать потолок по профилю поэтому незачем, а
вред прямой: у www.google.com начальное окно соединения — 192 КиБ, и туннель,
упёршись в такой потолок, отдавал бы десятки мегабит вместо сотен.

Снятое 24.09.2026 для сравнения:

| | cloudflare-quic.com | www.cloudflare.com | www.google.com | эвристика `cdn` |
|---|---|---|---|---|
| время простоя | 180 с | 180 с | 240 с | 30 с |
| initial_max_data | 10 МиБ | 10 000 000 | 192 КиБ | 15 МиБ |
| initial_max_stream_data | 1 МиБ | 1 000 000 | 128 КиБ | 6 МиБ |
| потоки bidi / uni | 100 / 3 | 100 / 3 | 100 / 103 | 100 / 103 |
| stateless_reset_token | нет | нет | есть | — |

Три однонаправленных потока — впритык: HTTP/3 тратит ровно три (управляющий и
два QPACK). Что этого хватает, проверено сессией на настоящем QUIC
(`TestCapturedProfileServesSession`), а не рассуждением.

Поле `stateless_reset` в профиле — наблюдение, а не настройка: свой токен
сервер отправляет всегда, потому что молчание на пакет с незнакомым
Connection ID само по себе признак.

**Чего через публичный API quic-go и `crypto/tls` сделать нельзя** (остаток
C1, честно): порядок и состав расширений ServerHello, выбор шифронабора
TLS 1.3 (Go выбирает его по наличию AES-NI), `ack_delay_exponent`,
`max_ack_delay`, `active_connection_id_limit`, `disable_active_migration`,
`max_udp_payload_size`. Это закрывается только патчем quic-go или форком.

## Мобильный клиент (Android)

Ядро то же самое; различается лишь то, кто создаёт интерфейс. На desktop это
делает сам клиент, на телефоне — система, а приложению выдаётся готовый
дескриптор. Из-за этого запуск разделён надвое: `VpnService.Builder` требует
адрес ДО создания интерфейса, а наш адрес выдаёт сервер уже ВНУТРИ
установленной сессии.

```
Connect(config, protector, events) → JSON: адреса, маршруты, DNS, MTU
        ↓                 приложение строит Builder и зовёт establish()
Attach(fd)                ядро начинает перекачку пакетов
```

`Protector.Protect(fd)` — это `VpnService.protect`: без него пакеты самого
туннеля пойдут В туннель, и он замкнётся сам на себя. Отказ защиты ядро
считает ошибкой и не продолжает.

Сборка требует Android SDK и NDK (`mobile/build-aar.sh`, затем `gradlew`),
подробности — в `mobile/README.md`.

**Как это проверено.** Собрать Android в контейнере разработки нечем, но сам
контракт к Android не привязан, и на Linux он воспроизводится целиком.
`test/e2e/androidsim` играет роль системы: сам открывает TUN, отдаёт ядру
голый дескриптор, настраивает интерфейс по тому же JSON, который увидит
Kotlin, и защищает сокет меткой вместо `protect`. Дальше работает ровно тот
код, который поедет на телефон.

```sh
sudo go test -tags e2e ./test/e2e/ -run TestAndroid -v
```

Проверяется: трафик через туннель, поднятый мобильным ядром (2 МБ, ping,
NAT); что ядро просит у системы разумное (адрес из пула, маршрут по
умолчанию, MTU, и никакого `::/0` без адреса IPv6); что ротация не требует
перестройки интерфейса (адрес держится арендой) и не теряет пакетов; что
после остановки не остаётся правил маршрутизации. Мутация: приложение
говорит «сокет защищён», не защитив его, — туннель обязан перестать работать.

Не проверено: сборка `core.aar` и само приложение на Kotlin — для этого нужны
SDK, NDK и телефон.

## Сквозные тесты

```sh
sudo go test -tags e2e ./test/e2e/ -v            # нужны ip, ping, curl
sudo MASQUEVPN_BENCH=1 go test -tags e2e ./test/e2e/ -run Throughput -v
```

Стенд: `gv-cli` ⇄ `gv-srv` ⇄ `gv-inet` («интернет» 198.51.100.10 без маршрута к
сети клиентов). Проверяется: без туннеля интернета нет; ping (в т.ч. шлюза),
curl, UDP, TCP 20 МБ вниз/вверх, 8 параллельных загрузок; MTU 1500 работает
без единого ICMP (кадры), при расписании профиля в простое идёт около 60
датаграмм в секунду против единиц без него (счётчики интерфейса), сервер
объявляет параметры из профиля, при ротации TLS-сессия возобновляется;
фоновые DNS-запросы
видны наблюдателю за шлюзом и приходят с НАСТОЯЩЕГО адреса клиента, а не с
туннельного (снятие пометки сокета роняет тест); «интернет» видит
адрес сервера (NAT), а без NAT ответы не возвращаются; чёрная дыра MTU в обе
стороны для обоих транспортов; подрезка MSS; ротация каждые 2 с под нагрузкой
без смены адреса (и все сессии открываются сразу со своим адресом);
переподключение после перезапуска сервера — не дольше десяти секунд; выживание
после блокировки канала (пауза между попытками растёт, адрес сохраняется);
`curl -X CONNECT` не получает документ; встроенный сайт отвечает всеми
страницами; чужой ключ → 404 и ни одной сессии; после остановки клиента не
остаётся правил и интерфейса.
Утилиты `ip`/`ping`/`curl` нужны только стенду — бинарники их не вызывают.

### Взгляд наблюдателя на канале

```sh
sudo go test -tags e2e ./test/e2e/ -run TestDPIObservation -v
```

`test/e2e/dpitap` — «пассивный DPI»: сырой сокет на канале между клиентом и
сервером, разбор Ethernet → IP → UDP → открытая часть заголовка QUIC и отчёт
о том, что видно снаружи: размеры и ритм пакетов, объёмы и асимметрия, самая
длинная пауза, посекундный профиль, рукопожатие целиком (версия, длины
Connection ID, размеры Initial-пакетов). Часть проверок закреплена
утверждениями теста: первый пакет клиента 1250 байт с DCID в 8 байт (как у
Chrome), Connection ID сервера не короче восьми байт.

Тесты `tun` и `netsetup` работают в собственном network namespace: тестовый
бинарник перезапускает сам себя с `CLONE_NEWNET` (без root — пропускаются).

### Сборка с uTLS

```sh
go build -tags utls ./...
go test  -tags utls ./...
```

Без тега пакет `utlsquic` компилируется в заглушку, а `Dial` возвращает `ErrNotBuilt` —
основная сборка остаётся лёгкой. Обе конфигурации проверяются тестами в паре.

Как это устроено и почему именно так:

```
uquic (форк quic-go с uTLS)          — ClientHello Chrome, форма Initial-пакета, длина CID
  └─ internal/utlsquic/h3.go         — свой минимальный HTTP/3: SETTINGS,
     (наш код, ~330 строк)             Extended CONNECT, DATA-фреймы, HTTP-датаграммы
       └─ masque.NewClientConn       — капсулы, политика адресов, паддинг, cover
                                       (то же ядро, что и у обычного клиента)
```

От uquic берётся **только QUIC-слой**. Его собственный http3 не подошёл по двум
причинам: он написан под `qpack v0.4`, а quic-go v0.59 требует `v0.6` (вместе в одном
модуле они не живут), и в нём вообще нет HTTP-датаграмм, без которых CONNECT-IP
невозможен. Поэтому ядро вынесено за интерфейс `masque.Stream` — и работает поверх
обоих транспортов без изменений.

**Чего это не даёт:** uquic v0.0.6 — старая и мало поддерживаемая зависимость,
и её собственные профили ограничены Chrome 115 / Firefox 116 (профиль по
умолчанию снят нами с живого браузера, см. «Свежий отпечаток»). Библиотека
подключена копией с двумя правками — `third_party/uquic`, разбор в
`MASQUEVPN-PATCH.md`. Серверная сторона отпечаток не меняет.

### Свежий отпечаток

**Профиль по умолчанию — `chrome-153`,** снятый с живого браузера утилитой
`fpcapture` и встроенный в бинарник (`internal/utlsquic/profiles/`). Собрать
такой профиль из кода uquic невозможно: в нём нет ни постквантового key_share,
ни trust_anchors, ни нового номера ALPS (17613 вместо 17513).

Что пришлось починить, чтобы снятый отпечаток заработал (2026-09-24):

- **ClientHello Chrome 153 не помещается в одну датаграмму** — около 1916 байт
  при датаграмме 1250, то есть два Initial-пакета. uquic этого не умел и падал с
  `failed to reassemble CRYPTO frames`. Исправлено в копии библиотеки, см.
  `third_party/uquic/MASQUEVPN-PATCH.md`.
- **Готовый профиль жил ровно одно подключение.** uTLS дописывает в объекты
  расширений состояние рукопожатия, и второй дозвон тем же объектом падал с
  `tls: internal error`. Для клиента это означало бы: первая сессия поднялась, а
  после первой же ротации соединения — больше никогда. Теперь `CustomSpec`
  принимает саму запись (`*Fingerprint`), и профиль собирается заново на каждый
  дозвон.
- **Размер первого Initial-пакета плавал** (1252–1295 вместо постоянных 1250):
  криптоданные набирались под завязку, а перекладывание их в свои кадры пакет
  раздувало. Добавлен запас под заголовки кадров.
- **ECH выбрасывается из отпечатка**, хотя Chrome 153 его шлёт (218 байт).
  Российский DPI режет соединения с `encrypted_client_hello` по самому факту
  наличия расширения, так что точное повторение браузера здесь означало бы не
  пройти вовсе. Проекту ECH и не нужен: SNI открыт по решению от 2026-09-17,
  скрывать нечего. Отпечаток отличается от снятого на одно расширение — размен
  осознанный: «Chrome с выключенным ECH» живое сочетание (ECH отключается
  флагом и групповой политикой), а соединение, которое режут на рукопожатии, не
  спасёт никакая точность.
- **ALPS восстанавливался под старым номером** 17513, а Chrome 153 шлёт 17613 —
  расхождение в одном поле, читаемом прямо из ClientHello.

Почему профиль нельзя было просто взять из uTLS: он обновлён до v1.8.2 (в нём
есть спеки Chrome 120/131/133), но **построить из них QUIC-профиль нельзя** —
проверено 2026-09-17:

- QUIC-профиль обязан нести список **транспортных параметров QUIC** (uquic
  вызывает `PopulateFromUQUIC` над ним). В спеке для TLS-over-TCP их нет и быть
  не может: у TLS поверх TCP таких параметров не существует. Это отдельная ось
  отпечатка, и вывести её из первой невозможно.
- Попутно вывод упирается в цепочку расхождений: версии TLS → ALPN (h2 вместо
  h3) → supported_versions (TLS 1.2 и GREASE), а у Chrome 131/133 ClientHello
  ещё и не помещается в компоновку Initial-пакета от Chrome 115 (ECH и
  постквантовый обмен ключами).

Результатом был бы не «Chrome 133», а химера: TLS-расширения от 133,
транспортные параметры от 115 — сочетание, которого нет ни у одного живого
клиента. Отпечаток «почти Chrome» детекторы ловят лучше, чем точный отпечаток
старой версии, поэтому такой профиль сознательно не добавлен.

**Как обновлять отпечаток.** Есть готовый конвейер: снятие с живого браузера →
JSON → восстановление профиля. Перекомпиляция не нужна.

```sh
# на машине с браузером и обычной сетью
go build -tags utls ./cmd/fpcapture
./fpcapture -addr :8443 -out chrome.json -source "Chrome 141, macOS"
# затем направить браузер:
#   chrome --origin-to-force-quic-on=ваш.домен:8443 https://ваш.домен:8443/
```

В коде:

```go
fp, _ := utlsquic.LoadFingerprint("chrome.json")
spec, _ := fp.Spec()
cfg := utlsquic.Config{/* ... */ CustomSpec: spec}
```

«Обновить отпечаток» = перезапустить `fpcapture` и подменить JSON, хоть по
расписанию в CI. В клиенте это поле `fingerprint_file`.

Про ECH: в проекте его нет. Настоящий ECH не используется (SNI открыт), а
расширение `encrypted_client_hello` из снятого отпечатка **выбрасывается** —
российский DPI режет соединения с ним сразу, по одному факту наличия. Из записи
переносятся: расширения в порядке отправки с сырыми байтами (включая
неизвестные — GREASE и будущие), шифронаборы, транспортные параметры QUIC,
размер датаграммы, длины Connection ID и номер первого пакета.

Конвейер проверен **круговым тестом** (`TestFingerprintRoundTrip`): отпечаток
снимается с нашего же клиента, сохраняется, восстанавливается, подключается — и
набор расширений с транспортными параметрами сверяется с исходным. Браузер в нём
не участвует, поэтому подмена источника на настоящий Chrome — это смена входных
данных, а не логики.

Снять отпечаток именно с браузера в контейнере разработки не вышло: Chromium 141
в окружении есть, но QUIC на loopback он не выполняет (netlog показывает
`QUIC_ATTEMPT`, затем `QUIC_CONNECTION_CANCELLED`, до сокета не долетает ничего),
внешнего интерфейса у контейнера нет, а UDP наружу закрыт. Нужна машина с
браузером и обычной сетью — сам конвейер к этому готов.

**Автообновление библиотеки не поможет:** у uquic нет версий выше v0.0.6,
новых встроенных профилей не появится. Поэтому свежесть отпечатка держится не на
библиотеке, а на `fpcapture`: снять с браузера и подменить файл.

**Известное расхождение:** в QUIC-профиле Chrome 115 из uquic вообще нет GREASE,
хотя настоящий Chrome его шлёт, — неточен уже сам встроенный профиль. В снятом
Chrome 153 GREASE-расширений нет тоже, но это не наша правка, а то, что реально
ушло с браузера: GREASE у него остался только в транспортных параметрах QUIC.

## Сборка

Требуется Go 1.24+. Используется `quic-go v0.59.0` — последняя версия, которой хватает Go 1.24
(v0.60+ требует Go 1.26).

Библиотека uquic подключена копией из `third_party/uquic` (две правки, разбор —
в `third_party/uquic/MASQUEVPN-PATCH.md`): без них снятый с браузера отпечаток не
воспроизводится, а своих версий выше v0.0.6 у uquic нет.

Модули `golang.org/x/*`, `go.uber.org/mock`, `gopkg.in/*` подменены в `go.mod` через
`replace` на зеркала GitHub — это нужно в окружениях, где доступен только github.com.
Если `proxy.golang.org` недоступен:

```sh
export GOPROXY=direct GOSUMDB=off GOTOOLCHAIN=local
go test -race ./...
```
